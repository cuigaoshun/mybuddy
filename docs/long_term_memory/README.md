# 长期记忆方案

本文档用于说明陪伴型 Agent 当前阶段的长期记忆最小方案。

这份方案的目标不是一次性把完整记忆系统全部做完，而是在不打破现有一期主链路边界的前提下，为后续长期记忆能力留出稳定扩展点。

当前仓库已经具备以下基础：

- 飞书消息接入与归一化。
- `router` 层的主流程编排。
- `chat_memory` 为核心的消息记忆存储与检索。
- `ChatSessionInfo` 为核心的会话级元信息维护。
- Agent 图中的最近消息读取、长期记忆召回和上下文组装。

因此，这里的重点不是重新发明一套全新的记忆架构，而是在现有 `chat_memory + memory abstraction + agent context` 基础上，补出长期记忆的最小闭环设计。

## 目标

长期记忆在这个项目里的作用，不是简单保存聊天记录，而是帮助 Agent 形成持续性的用户理解。

当前阶段的长期记忆主要服务于以下目标：

1. 记住用户的稳定属性。
2. 记住用户的长期偏好。
3. 记住用户与 Agent 之间的关系状态。
4. 把对当前回复真正有帮助的长期信息注入上下文。

当前阶段不追求：

- 完整事件图谱。
- 多层级记忆治理后台。
- 复杂人工审核流。
- 独立记忆服务拆分。

## 设计原则

### 1. 保持现有模块边界

长期记忆仍然属于 `memory` 范畴。

- `router` 只负责调用编排和触发。
- `agent` 只负责消费上下文，不负责直接操作底层存储。
- `gateway` 不直接关心长期记忆细节。
- PostgreSQL 仍然只是当前实现，业务层继续依赖抽象接口。

### 2. 会话级与用户级信息分开

这里仍然要明确区分两类信息：

- 会话级信息：当前会话相关的时间、状态、租约与流程控制信息。
- 用户级信息：可跨多次对话复用的长期理解。

`ChatSessionInfo` 继续只承载会话级信息，不直接保存长期记忆正文、用户画像正文或关系状态正文。长期记忆应作为 `memory` 层中的独立能力存在，由 Agent 图在需要时主动读取。

### 3. 上下文只注入必要信息

长期记忆进入模型上下文时，不应该原样倾倒完整存储内容。

当前阶段只注入两类内容：

- 当前时间。
- 长期记忆摘要与用户属性的精简结果。

最近对话、历史证据召回等内容，继续沿用当前图中的既有链路处理。

### 4. 同步链路保持轻量

主回复链路当前已经承担消息入库、租约竞争、Agent 回复生成与发送。

因此长期记忆相关逻辑在同步链路里只能做轻量整理或触发，不能把重型总结、批量扫描或复杂异步补偿塞进 `router` 主流程。

## 数据边界方案

当前 `ChatSessionInfo` 只承载会话级元信息和回复租约信息。

这个边界在长期记忆引入后仍然保持不变。

### 1. `ChatSessionInfo` 不扩长期记忆正文

`ChatSessionInfo` 不建议新增长期记忆摘要、用户属性 JSON 或关系状态等正文型字段。

原因：

- 它当前的职责很清楚，就是会话级元信息与回复租约。
- 长期记忆天然是用户级能力，不应绑死在单个 session 结构上。
- 如果把长期记忆正文塞进 `ChatSessionInfo`，后续很容易把会话状态与用户画像混成一个模型。

因此当前阶段建议保持：

- `ChatSessionInfo` 只负责会话状态。
- 长期记忆由独立仓储抽象负责。
- Agent 在图内按需读取长期记忆。

### 2. 长期记忆独立建模

长期记忆建议作为 `memory` 层里的独立用户级记忆对象存在。

当前最小方案里，可以先把长期记忆收敛成两个核心结构：

- `long_term_memory_summary`：供上下文注入使用的长期记忆摘要。
- `user_profile_json`：供程序化读取与更新的结构化用户属性。

这两个结构都应挂在独立的长期记忆仓储抽象下，而不是挂在 `ChatSessionInfo` 上。

### 3. `user_profile_json`

`user_profile_json` 建议固定顶层结构如下：

```json
{
  "profile": {},
  "preferences": {},
  "relationship": {}
}
```

其中：

- `profile`：用户基础信息，例如昵称、职业、城市、身份描述。
- `preferences`：长期偏好，例如语言、回复风格、交流习惯。
- `relationship`：用户与 Agent 的关系状态。

### 4. `relationship.affinity`

这是本次需求里最关键的一部分。

“用户对 agent 的好感度”建议放在独立长期记忆里的 `user_profile_json.relationship` 中，而不是单独拆成数据库顶层列。

建议结构：

```json
{
  "relationship": {
    "affinity": {
      "level": 1,
      "confidence": 0.8,
      "updated_at": "2026-07-12T10:00:00Z",
      "notes": "用户近几轮对话中更主动表达信任与依赖"
    }
  }
}
```

其中：

- `level`：建议用粗粒度整数，例如 `-2 ~ 2`。
- `confidence`：表示当前判断置信度。
- `updated_at`：最后更新时间。
- `notes`：简短依据说明。

当前阶段不建议使用过细的百分制好感度。陪伴型场景里的关系判断本身就有模糊性，粗粒度更稳，更便于后续纠偏。

### 5. 长期记忆元信息

长期记忆本身仍然需要更新时间、来源与处理状态，但这些元信息应属于长期记忆仓储自己的模型，而不是会话信息模型。

例如可以在长期记忆对象上维护：

- `updated_at`
- `last_processed_message_id`
- `source_message_ids`
- `version`

## 当前时间的处理方式

这次需求里提到“在 `ChatSessionInfo` 里再加上当前时间”，这里更推荐把“当前时间”视为上下文装配时的运行时数据，而不是长期持久化字段。

原因很简单：

- 当前时间是每次生成回复时的瞬时值。
- 它不是会话状态，也不是长期记忆。
- 如果落库存储，很快就会过时。

因此当前时间更合适的做法是：

- 在组装 Agent 上下文时动态生成。
- 和 `retrieve_memory` 取回的长期记忆结果一起写入上下文视图。

也就是说，这里的“当前时间进入上下文”不依赖 `ChatSessionInfo` 扩字段，而是依赖上下文装配时的运行时注入。

## 上下文注入方案

当前阶段，上下文层面对长期记忆只保留最小注入。

建议在现有图流程里，把长期记忆读取职责放到 `retrieve_memory`，再由上下文装配节点消费读取结果。

- 当前时间。
- 长期记忆摘要。
- 用户属性快照。

也就是说：

- `retrieve_memory` 负责读取消息级相似召回和用户级长期记忆。
- `assemble_context` 负责把读取结果格式化为模型可消费的上下文。

注入原则如下：

### 1. 当前时间

用于帮助 Agent 判断：

- 白天/夜晚等时段语境。
- 节奏感与陪伴语气。
- 时间相关回复的自然性。

### 2. 长期记忆摘要

用于帮助 Agent 快速理解：

- 这个用户是谁。
- 用户长期在意什么。
- 用户与 Agent 的关系目前处于什么状态。

### 3. 用户属性快照

用于帮助 Agent 做更细粒度的个性化适配，例如：

- 默认使用中文还是其他语言。
- 更偏技术型还是偏陪伴型表达。
- 在互动上是否适合更亲密或更克制。

### 4. 不直接注入完整 JSON 原文

虽然底层保存的是结构化 `user_profile_json`，但喂给模型时应做精简与格式化，避免把无关字段、空字段、内部状态字段直接暴露给上下文。

## retrieve_memory 读取方案

长期记忆的读取，建议统一放在 `retrieve_memory` 节点，而不是放在 `ChatSessionInfo` 读取流程里。

这样做有几个直接好处：

- 长期记忆读取与现有记忆召回节点职责一致。
- `ChatSessionInfo` 不会被扩成用户画像容器。
- 后续如果长期记忆来源变多，仍然可以统一从 memory retrieval 层扩展。

### 1. `retrieve_memory` 读取两类内容

`retrieve_memory` 当前已经承担“记忆读取”职责，后续可以在这里合并两类 memory：

- 消息级记忆：最近历史、相似消息、证据窗口。
- 用户级长期记忆：长期摘要、用户属性、关系状态。

### 2. 输出统一的 memory snapshot

`retrieve_memory` 不应该把长期记忆直接塞到 prompt，而应该先把结果写入统一的 memory snapshot/state 字段。

这个 snapshot 至少应包含：

- `long_term_memory_summary`
- `user_profile_json`
- `retrieved_memory_hits`

### 3. assemble_context 只负责消费

在这个方案下：

- `retrieve_memory` 负责取回长期记忆。
- `assemble_context` 负责把长期记忆摘要、用户属性快照、当前时间和近期消息整合成最终上下文。

这样图内职责会更稳定：

- 读取在 `retrieve_memory`
- 组装在 `assemble_context`
- 生成在 `chat_model`

## 长期记忆更新流程

当前阶段建议把长期记忆更新拆成两个动作：提取候选信息、合并到独立长期记忆对象。

### 步骤 1：提取长期有效信息

从一轮或一段对话中提取：

- 用户稳定属性。
- 长期偏好。
- 与 Agent 关系变化信号。
- 重要经历或长期有效事件。

不进入长期记忆的内容包括：

- 一次性临时请求。
- 短时瞬态情绪。
- 纯事务型闲聊。

### 步骤 2：生成结构化候选结果

建议长期记忆提取工具输出结构化候选，而不是直接覆盖最终结果。

候选输出可以类似：

```json
{
  "summary_candidates": [
    "用户更偏好中文交流，且希望回复更自然一些"
  ],
  "profile_updates": {
    "preferences": {
      "language": "Chinese",
      "response_style": "warm"
    },
    "relationship": {
      "affinity": {
        "level": 1,
        "confidence": 0.75,
        "notes": "近几次互动更愿意表达情绪和依赖"
      }
    }
  }
}
```

### 步骤 3：合并而不是直接覆盖

长期记忆更新时要遵守以下规则：

- 已有稳定事实不要轻易被一次对话覆盖。
- 新信息如果和旧信息冲突，应优先保守处理。
- 关系变化可以渐进调整，不要因为一次表达剧烈跳变。
- 好感度更新以趋势为主，不以单轮情绪为主。

### 步骤 4：更新长期记忆对象

合并完成后，写回：

- `long_term_memory_summary`
- `user_profile_json`
- `updated_at`
- `last_processed_message_id`

## 工具与服务职责建议

当前阶段可以把长期记忆相关职责收敛为一层轻量工具/服务，而不是直接把逻辑写散在 `router` 和 `agent` 里。

建议职责如下：

### 1. 长期记忆提取工具

职责：

- 读取对话片段。
- 提取长期有效信息。
- 产出结构化候选结果。

### 2. 用户属性合并工具

职责：

- 对 `user_profile_json` 做规则化更新。
- 控制覆盖、保留、冲突处理。
- 更新好感度等关系信号。

### 3. 长期记忆更新服务

职责：

- 把长期记忆摘要和用户属性写回独立长期记忆仓储。
- 维护更新时间和处理游标。

## 同步链路与未来异步链路

### 当前阶段：同步链路只做最小更新

在现有主流程中，长期记忆相关动作只建议做轻量操作：

- 在用户消息和助手回复完成后，基于本轮对话提取少量候选信息。
- 将候选结果合并到独立长期记忆对象。

这一步的目标是先打通最小闭环，而不是追求完美记忆质量。

### 后续阶段：异步整理进入 workers

未来如果长期记忆提取变重，或者需要扫描历史消息补做整理，应把执行主体放到 `workers` 或等价后台层，而不是继续堆在 `router` 主流程里。

这符合当前仓库的模块边界要求：后台摘要、补偿、扫描、沉淀类逻辑应归后台层负责。

## APScheduler 方案说明（当前只写文档，不实现）

后续可以使用 `APScheduler` 做定时扫描，但当前阶段只作为文档方案保留，不进入本次实现。

建议思路如下：

1. 通过定时任务扫描“还未进入长期记忆整理”的对话。
2. 扫描依据以长期记忆对象中的 `last_processed_message_id` 或等价游标为主。
3. 每次扫描只认领一批待处理会话，避免全表盲扫。
4. 真正的 AI 分析与长期记忆合并放到后台处理逻辑里完成。
5. 处理成功后更新长期记忆摘要、用户属性和处理游标。

这里 `APScheduler` 更适合作为“定时触发器”，而不是把大段 AI 分析直接塞进调度线程里。

## 一期建议落地范围

如果只做当前最小方案，一期建议范围如下：

### 做

- 新增长期记忆仓储抽象。
- 新增长期记忆摘要与结构化用户属性模型。
- 在 `retrieve_memory` 中读取长期记忆。
- 在上下文里只注入当前时间和长期记忆快照。
- 设计长期记忆提取与合并接口。

### 先不做

- APScheduler 实际调度实现。
- 历史全量回扫。
- 独立长期记忆表拆分。
- 复杂人工审核与回滚机制。
- 多层级关系建模。

## 总结

当前仓库最适合的长期记忆最小方案，不是另起一套大而全的记忆系统，而是：

- 继续复用现有消息记忆链路。
- 保持 `ChatSessionInfo` 只承载会话级状态。
- 用独立长期记忆对象承载 `user_profile_json` 与 `long_term_memory_summary`。
- 在 `retrieve_memory` 中统一读取消息级记忆与用户级长期记忆。
- 在上下文里只放当前时间和长期记忆快照。
- 把未来历史扫描与重型整理留给 `APScheduler + workers` 的异步方案。

这样做的好处是边界清晰、改动集中、能先落下最小闭环，同时不给后续演进制造太大的结构包袱。
